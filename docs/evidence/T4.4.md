# T4.4 evidence: exact-plan review and approval

Date: 2026-09-28

## Result

Implemented a local plan-review flow that verifies the canonical plan digest,
checks expiry before and after consent, and persists an `Approval` only after
an exact digest was confirmed. Interactive review requires typing
`approve <digest>`; noninteractive review requires `--approve-digest HEX`.
`--yes` and profile arguments are rejected as approval. Decline, edited-plan,
expired-plan, and mismatched-digest paths do not invoke the approval store.
The review discloses recipe/tool purpose, version, download estimate and
origin, privileges, provider choices, cost/account-owner omissions, config
target and before/after hashes, manual steps, warnings, and reversal limits.
JSON mode writes one parseable document to stdout; prompts and diagnostics go
to stderr.
Missing selected-recipe details or a recipe version that differs from the
plan also blocks review.

The Plan contract has no cost estimate or account-owner fields. The review
states that these values are “not specified in plan”; it does not infer a zero
cost or an account owner. Persistence is injected through the consuming CLI
boundary and was exercised with `state.Store` in a temporary test directory.

`ParseApprovalArgs`, and the approval outcome errors did not yet exist.

command used a unique temporary directory under `/Volumes/BuildOffload` for

command. The existing shared Go cache remained at
`/Volumes/BuildOffload/go-build`.

failed before assertions with `no space left on device`. The coordinator

Guard-disabled negative evidence: in the isolated worktree, the canonical
digest equality condition in `validateReviewPlan` was temporarily changed to
`if false && digest != plan.Digest`. With a fixed test clock, the edited-plan
subtest then failed because review returned `err=<nil>` and persisted an
approval for the edited plan. The test process exited 1 as expected. The
original source was restored in a `finally` block; the scoped suite passed
again afterward. The combined go test run passed both the `TestReview` cases
and separately named `TestExactDigestApproval` case.

The tests use synthetic plans, an in-memory approval input, and temporary
state only. No project files, installations, provider calls, or config writes
were performed.

## Limits

The task owns only the review flow and tests, so it does not wire a command
handler or approval persistence policy into `cmd/anza`. Callers must supply
the current catalog recipes and a durable approval-store callback. This task
does not claim platform qualification or certification.
