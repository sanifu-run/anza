## Conservative public-limit envelope

To avoid relying on unknown route behavior, the upper-bound estimate uses the
published 1,050,000-token context and 128,000-token maximum output, and applies
the higher tier's rates to every token. This is intentionally conservative:
the input and output maxima are treated as independent rectangular bounds even
though they cannot all be consumed simultaneously within one context window.
The separate reasoning allowance below is also deliberately double-counted.

Conversion: at a rate of `$R per 1,000,000 tokens`, a token allowance `N`
costs `N × R` microUSD, since one dollar equals 1,000,000 microUSD.

| Reservation component | Bound × price | microUSD/request |
|---|---:|---:|
| Input | 1,050,000 × $0.20/M | 210,000 |
| Visible output | 128,000 × $0.75/M | 96,000 |
| Reasoning allowance | 128,000 × $0.75/M | 96,000 |
| **Total conservative reservation** | **$0.210 + $0.096 + $0.096** | **402,000 ($0.402)** |

Reasoning is included within completion-token usage for OpenAI's documented
token accounting; it is not a separate additional charge when already counted
as completion output. The third row is an intentionally duplicative safety
reserve because actual gateway limit semantics and reporting are not verified.
It must not be represented as a forecast of billed usage.

At this envelope, the approved $1/day cap admits only
`floor(1,000,000 / 402,000) = 2` full-envelope provider requests per day.
Twelve requests in one conversation reserve 4,824,000 microUSD ($4.824); 10
conversations at 12 requests each reserve 48,240,000 microUSD ($48.24/day).
If every one of 120 logical calls were a recommendation that needed a repair,
the code path could make up to 240 provider requests, or 96,480,000 microUSD
($96.48/day) at this envelope. These figures demonstrate that public model
limits alone cannot support the candidate 10-session / 12-call pilot within
the approved $1/day cap.

## Conditional application-cap scenario

If—and only if—the active gateway is verified to honor Chat's `max_tokens=2048`
as a hard cap on all completion tokens (including reasoning), one may use
`2048 × $0.75/M = 1,536` microUSD as an upper bound for completion billing at
the higher rate. The source does not prove that gateway behavior. Preserving
the full public context input allowance and separately double-reserving 2,048
output and 2,048 reasoning tokens gives:

| Reservation component | Bound × price | microUSD/request |
|---|---:|---:|
| Input | 1,050,000 × $0.20/M | 210,000 |
| Output, conditional on gateway honoring the cap | 2,048 × $0.75/M | 1,536 |
| Separate reasoning safety allowance | 2,048 × $0.75/M | 1,536 |
| **Conditional total** | **$0.210 + $0.001536 + $0.001536** | **213,072 ($0.213072)** |

At that conditional rate, 120 requests reserve 25,568,640 microUSD
($25.56864/day); the daily cap admits four complete envelopes. Up to 240 calls
including repairs reserve 51,137,280 microUSD ($51.13728/day). This remains far
above the approved cap. It is not an accepted setting or evidence that the
pilot fits.

leave input/output/reasoning reservation configuration unset. No enablement,
