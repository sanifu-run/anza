## Synthetic project review

No real participant project was approved or supplied, and none was inspected. I manually walked the workflows against this explicitly fictional scenario: **Pocket Ledger**, a tiny existing Go command-line tool with a configuration parser; its participant wants clearer invalid-input errors while keeping the saved format stable. This is a scenario review, not a model run or a claim of human participant validation.

- `anza-scope` turns the request into an observable error-message goal and marks saved-format compatibility as a boundary.
- `anza-plan` orders a useful slice: identify current parser behavior, add a focused failing case, implement the message change, and check format preservation.
- `anza-build` limits edits to the relevant parser and tests, preserving unrelated work.
- `anza-check` selects only checks observed in the fictional project's instructions and reports whether format preservation was actually exercised.
- `anza-review` checks the changed error path, compatibility, data exposure, and scope, citing concrete findings.
- `anza-continue` records verified changes and checks plus the next bounded action without treating planned checks as completed.

The wording stays tool-neutral, so the same steps work in either supported agent harness. No repository-specific command is prescribed by the skills.
