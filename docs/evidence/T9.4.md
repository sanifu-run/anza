## Scope and output

Worktree: isolated branch `task/T9.4-integrity`, based on `cbb6e3c81d35c0a5c3256dc8d46c68fc8ab92085`.

This follow-up adds a concrete `crypto/ed25519` verifier and bounded HTTPS metadata source, wires `anza update` to a build-time base64 public-key slot, and makes absent or invalid keys fail closed. The verifier authenticates the exact metadata bytes. The source fetches the adjacent fixed-name detached signature and rejects redirects. The release builder emits the updater's `ReleaseMetadata` fields, Ed25519 algorithm/signature filename, and digests for both POSIX and Windows manifests. `artifact_digest` is defined as the SHA-256 of the canonical JSON map of manifest paths to their SHA-256 values, and the updater recomputes it.

The release build scripts require and embed canonical base64 for a 32-byte Ed25519 public key. Release workflow assembly checks that the repository public variable matches the protected PEM public key used to verify signatures. The public key slot is unconfigured here. The updater's metadata URL is supplied at runtime through `ANZA_RELEASE_METADATA_URL` and must point to an immutable HTTPS `.../release-metadata.json` URL. The CLI check remains read-only; this work does not add binary download or replacement.

Schema drift protection uses `schemas/SHA256SUMS` over the eight `*.schema.json` files. `scripts/schema-lock.py --write` updates the lock intentionally; default/`--check` mode fails on missing, changed, or added schema files. CI and release qualification invoke it and a negative-control script.
