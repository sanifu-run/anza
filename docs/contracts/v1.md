# Anza contract v1

Status: revision 2, founder-directed shared-chat implementation baseline; task T1.2 materializes schemas and validates fixtures before worker fan-out. No prior version has been implemented or published. Wire version is integer 1. Unknown fields/enums are rejected at new setup-specific boundaries; existing intake decoding remains compatible. Additive evolution requires a versioned compatibility decision. T1.2 is the sole public schema/type owner.

## Shared data

Anza domain JSON uses snake_case. Existing chat HTTP envelopes retain camelCase (requestId, expectedVersion, machineFacts, catalogVersion); explicit mappings are required in wire fixtures. All new fields use UTF-8, bounded strings, no NaN and UTC RFC3339 timestamps. Errors expose code/message/retryable/request_id, never raw upstream bodies. No interface accepts an arbitrary executable command from the LLM.

- `ProjectBrief`: schema_version, project_summary (1..4000 chars), desired_slice (0..2000), experience (beginner|developer), constraints (array <=20, strings <=500), known_stack (IDs <=20), project_kind (free description <=200), existing_project (bool). Optional client_project bool defaults false. Optional source {kind: learner_export, reviewed: true}; absent source means Anza interview. No name/contact/transcript token fields.
- `MachineFacts`: os (darwin|windows|linux), arch (amd64|arm64), os_version, distro_id/version when applicable, shell_kind, capabilities map of catalog IDs to status/version. No username, hostname, raw paths, hardware serials or installed-app inventory.
- `Recommendation`: schema_version, catalog_version, summary, selected_recipe_ids, selected_pack_ids, selected_exercise_id, reasons by ID, unresolved_questions, manual_steps (plain explanatory text), readiness_constraints. Limit selections to 30 recipes/10 packs. Manual steps cannot be automatically executed. No urls/commands/paths fields. Server validates, client revalidates against its installed catalog.
- `Recipe`: id, version, description, purpose, supported_platforms, prerequisites, detection, install_strategy, artifact metadata, privileges, license_notes, estimated_download_bytes, side_effects, verification, reversal_class. Strategies are typed: verified_archive, vendor_installer, package_manager, manual. Every strategy is a reviewed enum with fixed program/argument templates in code/catalog; never interpolate interview text into shell.
- `Pack`: id/version, skill IDs, prerequisites, license/provenance IDs, compatible agent versions, file digests. Skill names use anza- prefix. Each asset has origin/license/adaptation notes.
- `Plan`: schema_version, id, workspace_id, catalog_digest, facts_digest, recommendation_digest, created_at, expires_at (24h default), profile, provider choices per agent, operations, warnings, manual_steps, digest. Ordered operations carry id/kind/recipe_id/version/dependencies/target logical root/relative path/preimage hash/expected postimage hash/reversible/privilege/description. Bind digest to canonical JSON excluding digest field. Canonical encoding sorts map keys, preserves arrays and rejects duplicate keys before decoding.
- `Approval`: plan_digest, approved_at, disclosure_version. Never accepts just a boolean. Any edit, catalog version change or preimage drift invalidates approval.
- `Receipt`: schema_version, plan_digest, ordered operation states, owned_paths/keys, pre/post digests, backup references, timestamps, pending_manual_actions. Operation states planned -> running -> succeeded|failed|unknown|skipped; rollback states rolling_back -> rolled_back|conflict. Journal append and flush precedes effects.
- `CheckResult`: id, required, status, summary, next_action, evidence_kind (local|live|manual), checked_at. Live checks are never inferred from fixtures.

## Package seams

T1.2 creates value structs and validates their JSON fixtures. Consuming packages define minimal interfaces; do not put all services in domain.

- `platform.Inspect(ctx, root) (domain.MachineFacts, error)` is read-only.
- `planner.Build(facts, brief, recommendation, catalog, existingState) (domain.Plan, error)` is pure; deterministic clock/ID inputs must be explicit.
- `configedit.Plan(existing []byte, requested Patch) (Edit, error)` returns bytes and ownership delta without writing. Unknown syntax must preserve or refuse.
- `process.Run(ctx, Spec) (Result, error)` accepts program, argument array, explicit working dir/env policy, timeout and output limit. Sensitive values never enter Spec serialization/logging.
- `executor.Apply(ctx, Plan, Approval) (Receipt, error)` rechecks preimages and catalog, locks roots and records effects. Inject executor dependencies through its constructor.
- `doctor.Check(ctx, workspace, options) ([]CheckResult, error)` local by default; live checks require explicit option/confirmation.
- `credentials.Store` methods Put/Get/Delete use credential ID only; implementations own platform storage. No file fallback on unavailable keychain without a separate future decision; session-only input remains available.
- Chat adds a shared raw model helper on the existing `server`; `answerWithPrompt` remains its compatibility wrapper. Setup uses the same client/model/endpoint/runtime credentials and optional usage metadata, never participant agent keys.
- Chat `setupService` consumes existing server/store, common turn helpers and a setup quota adapter. Its handlers are registered by the shared server; no Anza server package is created.
- Cross-repository wire fixtures and recommendation catalog metadata are copied with version/digest provenance at build time. Neither Go module imports the other; Anza never needs private chat access at install/runtime.

## Shared chat HTTP API

These are planned additions/branches in the existing backend, not a new base URL. Existing intake request/response shapes are unchanged. No separate `/v1/sessions`, `/readyz`, invitation or bearer token contract exists. Legacy `/healthz` remains unchanged. New setup payloads are bounded to 32 KiB, strict one-object decoding, duplicate/unknown field rejection and no secret logging; legacy decoder behavior is preserved.

### Session and purpose

Generate 32 cryptographically random bytes on the CLI and hex-encode to 64 lowercase characters. Use `X-Conversation-Token` on all private requests, matching existing `conversationID` hashing. Never put it in URLs or logs. The server does not issue/recover a second session token. `requestId` follows the existing 16..64 ASCII alphanumeric/underscore/hyphen pattern and is stable across retries. Validate expectedVersion before a new mutation; replay identity is checked before rejecting the old version so completed identical requests are still replayable.

Conversation gains optional `purpose` and `setup` fields. Missing purpose remains intake. Setup creation sets purpose=setup immutably. A supplied existing intake token returns 409 on setup creation; do not convert it or import its transcript. Existing Conversation version/generation/TTL protect writes. Setup state contains protocolVersion, catalogVersion/digest, reviewed ProjectBrief or labeled approvedBriefText, reviewed MachineFacts, consentVersion, start request ID/body digest, status, recommendation and recommendationSourceVersion/contextDigest. Raw participant credentials and paths are prohibited.

All existing token/origin checks still apply; native requests can omit Origin as existing chat allows. Browser allowlists are not broadened. Setup handlers deny non-setup conversations. Shared route wrappers deny setup tokens on booking, brief mutation and title mutation without changing the legacy intake path. Administrative setup access requires the existing separate owner credential and explicit purpose filter. Error envelopes for existing routes remain their existing plain-text/status behavior; new setup handlers use a stable {code,message,retryable,requestId} JSON error shape. The client handles both deliberately.

### Questions versus recommendations

`/api/ask` remains a conversational response and can never be interpreted as an executable recommendation. Questions use a setup-only prompt with server-held history and reviewed facts. `/api/setup/recommendation` explicitly asks the existing model transport for schema-constrained JSON, validates it against the pinned catalog and persists it with source/context version. Strip no links/fields through the ordinary citation wrapper before JSON validation. New turn/context invalidates the recommendation. Learner brief approval does not approve installation; install approval remains local and digest-bound.

Setup requests retain existing chat message limits (1000 Unicode code points) and 64-KiB history bound, with a proposed 12-turn setup limit. Existing shared HTTP/model deadlines and 2048 max output tokens remain; title's 96-token special case must survive transport extraction. Provider optional structured-output parameters may be used only if qualified with the current route; strict post-response schema validation is always required. One repair attempt maximum under the same budget.

### Setup usage and replay

Persist setup reservations in a coordination DynamoDB table managed by the existing stack. Keep non-conversation rows out of transcript storage. Reuse existing AWS configuration/client; add only scoped transaction/update permissions. Use setup-wide daily and per-conversation caps; shared provider credit limits are separate. Current `allow` and `active` controls remain per-instance, not a durable whole-product financial cap.

Reserve conservative configured worst-case input/output/reasoning cost in integer micro-USD before the shared provider call. Missing price/cap disables setup calls only. Durable operation states distinguish pending, sent/unknown, completed, failed-before-send and deleted. Same requestId/body with completed output returns the cached output. A lease expiry after sent/unknown never authorizes another paid request automatically. Recommendation replay/versioning observes this same policy. A generation change/deleted session cannot revive old operations. Reconcile usage when provided; missing/ambiguous usage keeps the conservative reservation. Cleanup removes context/content while minimal non-content replay/budget metadata remains only for its disclosed TTL.

### Compatibility release contract

The public Anza catalog export contains IDs, descriptions, supported platform constraints and digests, never executable recipes or secrets. Chat embeds a reviewed copy and advertises supported protocol/catalog. Reject mismatch before model calls. Deploy additive backend with feature disabled, qualify all legacy website paths, enable setup, then publish the matching CLI. Rollback disables setup while preserving existing intake and conversations. Retention inherits the reviewed shared backend policy; setup email copies are off by default.

## CLI contract

`anza` starts the wizard; `anza setup --project PATH --profile beginner|developer [--brief FILE]`; `anza inspect --json`; `anza interview --resume ID`; `anza plan --project PATH [--json]`; `anza apply --plan FILE [--approve-digest HEX]`; `anza doctor [--live] [--json]`; `anza run codex|claude -- [agent args]`; `anza repair --project PATH`; `anza update [--check]`; `anza uninstall [--project PATH]`; `anza diagnostics --output FILE`; `anza version`.

No-argument bootstrap launches wizard only when a controlling terminal exists. Noninteractive invocation never waits for input, provisions paid resources or infers approval. Stdout contains only requested JSON in JSON mode, stderr holds diagnostics. Exit codes: 0 complete/local success; 2 input error; 3 manual action/unverified prerequisite; 4 external/network error; 5 conflict/approval stale; 6 unsupported target; 130 interrupted. Version/help succeed without network/state writes. EOF saves resumable local progress and exits 3; Ctrl-C cancels children and exits 130. `--approve-digest` is explicit consent to that plan, not permission for live model charges or elevated unrelated actions.
