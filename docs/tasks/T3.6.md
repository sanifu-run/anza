## Implementation steps

1. Add optional setup service field/initialization to existing server and register only additive setup routes. In /api/ask, dispatch existing setup-purpose conversations through setupService while retaining the legacy branch and response format.
2. Default ANZA_SETUP_ENABLED to false. A missing/invalid setup-only configuration disables setup capability and its routes with a clear status; existing health/intake/title/brief/booking still function.
3. Reuse provider secrets, shared HTTP process, storage and graceful shutdown. Apply quota/mode guards before provider calls; use shared allow/active exactly once per call. Do not introduce a new executable or health service.
4. Provide an opt-in loopback setup test fixture using the real shared router and fake storage/provider. Its startup writes a temporary ready file; no live credentials/model/calendar calls. This supports the Anza cross-repo CLI acceptance task.
5. Document additive API/config and gate rollout on existing website contact/intake/title/brief/booking regression results from the reconciled peer baseline.
