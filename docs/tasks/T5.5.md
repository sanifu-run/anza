## Implementation steps

1. Define per-project Python environments and Go tooling with one recipe per exact platform artifact. Pin versions and record vendor-published SHA-256, exact byte size, source and license; if integrity or exact size is unavailable, omit an automated recipe and leave the capability manual. Preserve existing interpreter/module versions. Where the coarse platform predicate cannot represent an OS/kernel floor, mark the recipe manual and state the floor in detection/verification; unknown OS-version facts never mean ready.
2. Separate CPU readiness from optional GPU/CUDA/remote-compute requirements. Zerfoo is optional where fit is established, never a universal ML requirement; no cloud/GPU resources are allocated. Packs must not encode mutually exclusive platform recipes as unconditional prerequisites; clients select a recipe using its supported_platforms. If no reviewed GPU capability exists, a GPU-required project remains manual/unmet.
3. Defer exercise descriptors until a versioned Exercise schema and loader validator exist. Do not download datasets or execute package scripts; any later existing-project check requires participant approval.

Provenance JSON uses the T5.1 catalog record shape: an array of `{id, source, license}` objects referring to primary official sources and named licenses.
