## Implementation steps

1. Add optional immutable Conversation.Purpose and Setup state to the existing Conversation type. Empty purpose remains legacy intake. Reuse conversationID, transcriptStore and existing DynamoDB CAS/TTL/generation behavior; do not create a new session/token store.
2. Define setup protocol/catalog context, start request ID/body digest, setup status, recommendation/source version and privacy consent fields in setup_state.go. Native CLI generates the existing 64-hex random recovery token; server persists only its SHA256 ID. Define backend-local wire types in setup_types.go from the public protocol fixtures; do not import the Anza module just to get types.
3. Make existing store serialization and conversation deletion preserve/remove setup state with the whole conversation. Extend summary purpose metadata for the later mail/admin boundary task. Keep all existing fields and legacy JSON behavior.
4. Add strict setup creation validation using store.Put(previous=0), immutable purpose and body digest replay. A legacy intake token cannot silently become a setup conversation.

## Acceptance criteria

- Legacy conversation fixtures still round-trip unchanged while setup fields survive DynamoDB CAS and restart fixtures.
- Matching start request replay returns the same setup state; changed body or intake-purpose token returns conflict.
- GET/DELETE through the existing conversation lifecycle restores/removes setup state; missing/expired records follow existing visibility rules.
